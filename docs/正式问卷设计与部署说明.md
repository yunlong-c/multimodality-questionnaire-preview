## 1. 文档边界

本说明记录当前正式问卷的研究实现，包括刺激编号、题目抽取、呈现格式随机化、参与者流程、数据保存、研究后台和 Netlify 部署。它用于回答“参与者实际看到了什么、系统如何随机、每条数据如何追溯、正式答卷如何确认已收到”等问题。

需要严格区分以下三类信息：

- **已确认事实**：已由当前代码、冻结 Catalog、素材审计或自动测试直接验证。
- **运行期事实**：只有在正式 Netlify 数据库、随机表和环境开关启用后才能验证。
- **尚未核实事项**：伦理审批、机构数据管理要求、正式发放资格等不属于代码测试可以替代的内容，须由研究负责人另行确认。

本说明不替代伦理申请书、预注册、统计分析计划或机构数据管理制度。

## 2. 研究设计概览

### 2.1 核心任务

参与者完成 5 道时间序列预测题。每道题呈现同一序列的前 20 期历史数据，参与者填写第 21 期的点预测。第 5 题除点预测外，还填写 5 个从低到高排列的可能数值及其对应概率，五个概率合计必须为 100%。

参与者页面采用中性任务说明，不提前介绍 Table、Graph、Video 之间的比较，也不暴露具体研究假设。

### 2.2 实验因素

主要呈现因素为三水平的被试间条件：

1. `table`：HTML 数值表；
2. `graph`：静态折线图；
3. `video`：动态逐期揭示图。

一次正式会话只分配一种呈现格式，同一参与者的 5 道题全部使用该格式。参与者不能自行选择格式，正常页面也不显示分组名称。

### 2.3 题目结构

| 题号 | 序列来源 | 作答角色 | 选择规则 |
|---|---|---|---|
| 第 1 题 | Pool 1 | `point_only` | 从 80 条中等概率抽取 1 条 |
| 第 2 题 | Pool 2 | `point_only` | 从 64 条中等概率抽取 1 条 |
| 第 3 题 | Pool 3 | `point_only` | 从 64 条中等概率抽取 1 条 |
| 第 4 题 | Pool 4 | `point_only` | 从 64 条中等概率抽取 1 条 |
| 第 5 题 | Pool 1 | `point_spd` | 从剩余 79 条中等概率抽取 1 条，不与第 1 题重复 |

在格式已经确定的条件下，单次会话中各题候选序列的抽取概率分别为 `1/80`、`1/64`、`1/64`、`1/64` 和条件概率 `1/79`。Pool 2 中 fast 与 slow 各 32 条，因此在不附加筛选的前提下，第 2 题抽到 fast 或 slow 的概率各为 `1/2`。

5 道题在实验开始时一次性固定。参与者使用“上一题”返回时，系统恢复原题及已填草稿，不重新抽题，也不改变顺序。

### 2.4 序列参数结构

冻结 Catalog 中共有 272 条真实序列：

| Pool | 数量 | Catalog 中保留的设计元数据 |
|---|---:|---|
| Pool 1 | 80 | `rho ∈ {0.2, 0.4, 0.6, 0.8}` |
| Pool 2 | 64 | `rho`、趋势方向 `up/down`、`beta`；另有 fast/slow 呈现变体 |
| Pool 3 | 64 | `rho`、趋势方向、baseline/变点条件、`tau_obs`、`beta1`、`beta2` |
| Pool 4 | 64 | `rho`、baseline/变点结构、`tau_obs`、方向、`sigma1`、`sigma2` |
| 合计 | 272 | 每条序列对应 Table、Graph、Video 三种呈现 |

上述元数据是 Catalog 中的技术字段。其理论含义和最终统计对比应以正式研究方案及统计分析计划为准，不能仅凭字段名临时推断。

## 3. 刺激目录与编号冻结

### 3.1 三层正式编号

每条序列保留三层正式标识：

- `sequence_uid`：稳定研究主键，例如 `MMQ-P02-FAST-ID019`；
- `canonical_key`：加入序列修订号，例如 `MMQ-P02-FAST-ID019@r01`；
- `presentation_uid`：加入呈现格式和呈现修订号，例如 `MMQ-P02-FAST-ID019@r01:GRAPH@p01`。

同时保留：

- `source_id`：工作簿正式 ID；
- `display_index`：工作簿展示顺序；
- `legacy_asset_no`：旧 PNG/GIF 文件名尾号；
- `pair_uid`：Pool 2 fast/slow 配对标识；
- `response_type`：该序列在当前题目中承担的作答角色。

### 3.2 旧素材尾号映射

| 条件 | `legacy_asset_no` 的来源 |
|---|---|
| Pool 1 | `display_index` |
| Pool 2 slow | `display_index` |
| Pool 2 fast | `source_id` |
| Pool 3 | `display_index` |
| Pool 4 | `display_index` |

Pool 2 fast 是必须特别核查的例外。例如：

- `sequence_uid = MMQ-P02-FAST-ID019`
- `source_id = 19`
- `display_index = 21`
- `legacy_asset_no = 19`

因此该序列的 Graph 和 Video 继续引用尾号 `_19` 的旧素材，不能按展示序号错误引用 `_21`。

已确认：

- Pool 1 采用 80 条 canonical 版本，旧 60 条版本不混入正式 Catalog。

## 4. 三种呈现格式

### 4.1 Table

Table 不使用历史 PNG，而是直接读取 Catalog 中的 20 个数值生成原生 HTML：

- 左栏显示第 1–10 期；
- 右栏显示第 11–20 期；
- 每栏包含“时期｜数值”；
- 数值保留两位小数；
- 20 个值按时间顺序各出现一次；
- 当前渲染器版本为 `html-table-v4-unified-dual-panel`。

HTML Table 的优点是移动端文字清晰、无需点开图片、可由浏览器自适应显示。正式数据记录 `renderer_version`，Table 的 `asset_sha256` 为空，但仍保留历史 Table PNG 的路径和哈希用于审计。

### 4.2 Graph

Graph 继续使用冻结的原始 PNG：

- 原文件、路径和 SHA-256 不变；
- 页面内按既定尺寸呈现；
- 点击图像可进入全屏遮罩；
- 支持关闭按钮、背景关闭、浏览器返回键和 Escape；
- 全屏打开次数及累计时长写入试次数据。

### 4.3 Video

Video 继续使用冻结的原始 GIF，并配合从同一 GIF 提取的终帧：

- GIF 完整加载成功后才开始播放计时和首次揭示；
- 首次揭示完成前锁定前后导航；
- 揭示完成后切换到该 GIF 的终帧，避免自动循环；
- 允许重播一次，重播额度跨返回访问保留；
- 返回已经看过的 Video 时直接显示终帧，不重新启动首次播放；
- 全屏时移动同一个图片 DOM 节点，不重新加载 GIF；
- 素材加载时长、尝试次数、状态、全屏次数和全屏时长进入试次数据；
- 加载失败时提供重新加载路径，不能把未完整呈现误记为完成播放。

## 5. 参与者流程

正式流程为：

1. 首页；
2. 参与说明；
3. 参与确认；
4. 题目准备与隐藏式格式分配；
5. 第 1–5 题；
6. 背景问卷；
7. 数据提交；
8. 完成页。

参与确认页保留参与时长、自愿参与及退出、数据保密性与确认框。手机端按钮顺序为“开始答题”在上、“返回”在下；桌面端为“返回”在左、“开始答题”在右，DOM、视觉和键盘焦点顺序一致。

预测题统一提示为：

> 请查看前 20 期历史数据并填写第 21 期预测值。

第 1 题只显示“下一题”；第 2–4 题显示“上一题／下一题”；第 5 题显示“上一题／下一页”。进入背景问卷后不再返回预测题。

点击“上一题”时保存草稿但不强制验证；点击“下一题”或“下一页”时严格验证。第 5 题要求：

- 五个可能数值完整填写；
- 数值从低到高，可相等但不能递减；
- 五个概率完整填写；
- 每个概率满足输入范围；
- 概率合计为 100%。

背景问卷当前记录性别、年龄、学历、相关经验和统计课程情况。参与者页面不显示刺激编号；只有 `?debug=1` 测试链接可显示研究核查标签。

## 6. 呈现格式随机化

### 6.1 正常分配

正式格式分配使用 Netlify Function、Netlify Database 和私有可变区组随机表：

- 随机化版本：`mmq-randomization-2026-07-v1`；
- 总分配位：3000；
- Table、Graph、Video 各 1000 个；
- 区组大小只取 6、9、12；
- 每个完整区组内三种格式严格等量；
- 区组大小和组内顺序由密码学随机源生成；
- 完整随机表只保存在私有文件和研究数据库，不进入公开 GitHub；
- 公开仓库只保留版本号与随机表 SHA-256 承诺。

参与者确认后，浏览器使用稳定的 `client_token` 调用 `POST /api/allocate`。数据库在事务锁内原子领取下一位置：

- 同一浏览器令牌重复请求返回原格式；
- 重复请求不占用新位置；
- 新会话得到新的 `session_id`，但格式身份可追溯；
- 分配一旦产生即永久占位，退出者的位置不回收；
- 3000 个位置表示最多 3000 个不同浏览器身份可开始，不代表一定获得 3000 份完成问卷；
- 预计有效完成数约 2000，额外位置用于退出、换设备、清缓存和重复访问的损耗。

只平衡“已分配人数”，不保证“最终完成问卷人数”严格相等。完成数差异必须在导出后报告。

### 6.2 本地应急随机

当分配 Function 出现网络超时、网络错误或暂时性服务端故障时，当前参与者可无感切换到浏览器 Web Crypto 等概率随机，并继续答题：

- 参与者看不到故障、数据库或分组信息；
- 应急结果立即写入当前浏览器本地存储；
- 刷新或恢复后保持同一格式；
- 服务器恢复后登记原应急结果，不强制改变格式；
- 应急记录标记 `allocation_method = client_fallback`；
- 未登记时标记 `allocation_status = unreconciled`；
- 应急分配尚未登记时，只向 Netlify Forms 写入一份明确标为未确认的紧急备份，不向权威答卷库写入；
- 参与者重试或刷新时，系统继续尝试登记原应急分配；登记成功后只允许更新 `allocation_status` 和 `fallback_reconciled_at` 两个审计字段，题目、答案、背景信息、格式和会话身份不得改变；
- 上述受控状态升级会重新计算 payload hash，但导出程序将其识别为同一答卷的审计状态升级，而不是答案冲突；任何试次或背景信息变化仍必须进入冲突清单；
- 登记成功后若权威数据库提交仍暂时失败，可为新的已确认 hash 再保存一份 Forms 紧急备份，参与者页面仍不得显示“已保存”；
- 应急样本进入正式数据，但统计分析须同时报告排除应急样本的敏感性结果。

以下情况不能触发本地应急随机：

- 正式收数开关关闭；
- 随机表耗尽；
- Catalog 或随机化版本不匹配；
- 非法请求；
- 明确的配置错误。

应急随机超过已开始人数的 1%，或连续出现 3 次时，当前参与者可以完成，但下一批发放应暂停排查。

### 6.3 测试入口

以下链接始终分类为 `test`，不得混入正式分析：

- Deploy Preview；
- `?preview=1`；
- `?debug=1`；
- `?format=table`、`?format=graph`、`?format=video` 等固定格式链接。

普通生产根链接才是正式入口。测试入口不应消耗生产随机表位置。

## 7. 作答状态与计时

每题在内存中维护独立状态：

- `visit_count`：实际进入该题的次数；
- `revision_count`：该题曾成功向前提交后，答案发生改变并再次向前提交的次数；
- `trial_started_at`：首次进入时间；
- `trial_submitted_at`：最终有效答案确认时间；
- `trial_duration_ms`：所有可见访问时长之和；
- `fullscreen_open_count`、`fullscreen_duration_ms`：全屏交互；
- `asset_load_duration_ms`、`asset_load_attempt_count`、`asset_load_status`：素材加载指标。

页面隐藏时暂停可见时长计算。正式 payload 对每个会话只保留 5 条唯一试次，每题一行，旧答案不会被追加为重复试次。

## 8. 数据保存与权威回执

### 8.1 权威保存标准

正式完成页只有在服务器返回数据库权威回执后才能显示“已保存”。不能把以下情况误写为已保存：

- 仅保存在浏览器本地；
- 仅开始了网络请求；
- Netlify Forms 接口返回但数据库未确认；
- 页面自行生成了一个未经过服务器验证的编号。

数据库成功写入后返回稳定的 `receipt_id`。该回执代表服务器已确认：

- 会话和分配信息有效；
- Catalog 和格式一致；
- 5 条试次结构有效；
- 完整 payload 已持久化；
- 同一 `session_id + payload_sha256` 的重复提交是同一份数据。

### 8.2 幂等与冲突

- 相同 `session_id` 和相同 payload hash 重复提交：返回同一 `receipt_id`，不产生第二份权威答卷；
- 相同 `session_id` 但 payload hash 不同：拒绝覆盖，写入冲突记录，需人工核查；
- 唯一例外是客户端应急分配从 `unreconciled` 到 `confirmed` 的受控审计状态升级；该升级必须在进入权威提交前完成，并由前端和导出工具共同断言除两个分配审计字段外内容完全不变；
- 服务器不可用时：保留冻结的待提交 payload，允许安全重试；
- 页面刷新后：优先恢复同一待提交内容，不能重新生成一份不同答案；
- 提交未确认时：允许参与者下载本人 JSON/CSV 备份，但不能显示“已保存”。

### 8.3 Forms 冗余

Netlify Forms 作为第二份传输与备份通道，不再是唯一权威来源：

- 正式数据与测试数据使用不同表单；
- 数据库写入成功后进入 Forms mirror outbox；
- 系统立即尝试镜像，失败后由定时任务重试；
- 镜像状态、尝试次数和最后错误供研究后台核查；
- Forms 中历史 `mmq-submission-v1` 记录保留为旧测试资料，不覆盖、不混入新正式数据。

Netlify Function 会从受信任的运行上下文读取提交来源 IP，并随权威答卷或冲突审计记录落库；Netlify Forms 后台也可能显示来源 IP。该信息不是前端主动生成的设备指纹，当前仅作为必要网络日志和质量控制资料保留。若后续将其用于实质分析，研究负责人应在统计分析计划中另行界定，不能在看到结果后临时决定。

## 9. 正式数据结构

每份会话至少包含：

- 会话：`session_id`、`participant_id`、开始/提交时间、总时长；
- 分配：`allocation_id`、随机化版本、分配方法、确认状态、分配时间；
- 研究版本：`stimulus_set_version`、`catalog_hash`；
- 格式：`format_assignment`；
- 分类：`formal` 或 `test`；
- 五条试次及背景问卷；
- payload 原文及 `payload_sha256`；
- 权威数据库 `receipt_id`；
- 部署上下文和必要网络日志；
- Forms 镜像状态。

每条试次继续保存：

- `sequence_uid`、`canonical_key`、`presentation_uid`；
- `source_id`、`display_index`、`legacy_asset_no`；
- Pool、variant、response type；
- 原素材路径、素材 SHA-256 或 Table renderer version；
- 点预测、概率分布、访问/修改/计时/全屏/加载字段；
- Catalog 中用于分析的序列元数据。

私有 `y21` 不进入浏览器 payload，也不进入参与者下载文件。

- 完整 JSON；
- `participants.csv`；
- `trials.csv`；
- Forms mirror 状态；
- submission conflicts；
- 必要的随机化审计摘要。

每次导出记录操作时间、范围、格式和共享管理员标识，不记录明文密码。

## 11. 网页设计与响应式原则

界面采用“学术极简”设计：暖灰背景、白色内容区、深海军蓝正文和单一蓝色强调色，避免渐变、过度圆角和厚重阴影。

响应式要求：

- 移动端正文与数字输入不小于 16px，避免浏览器自动放大输入框；
- 可点击区域不小于 44px；
- 适配安全区、软键盘、横竖屏和减少动画设置；
- 320px 以上不出现横向滚动；
- 手机、平板和桌面端保持相同研究内容与验证逻辑；
- 只压缩外层卡片、标题和非刺激区域的无效留白；
- Table 的宽度、行高、字号和双栏结构保持既定设计；
- Graph、Video 的页面内尺寸保持既定设计；
- Graph、Video 可全屏，Table 不提供全屏。

参与者页面不显示研究人员入口、测试横幅、刺激编号或内部保存机制。测试信息只在明确的测试 URL 中出现。

## 12. 部署架构

### 12.1 代码与发布链路

正式发布链路为：

1. 本地独立 Netlify 工程；
2. GitHub 私有开发分支和 Pull Request；
3. Netlify Deploy Preview 用于代码审查；
4. 测试通过后合并到 GitHub `main`；
5. Netlify 从 `main` 生成 Production deploy；
6. 正式根地址供参与者访问。

`Deploy Preview` 是 Pull Request 的开发预览地址，URL 形如：

`https://deploy-preview-4--sequence-prediction-study.netlify.app/`

它不是正式发放地址。预览页面底部出现的灰色工具条属于 Netlify Drawer，不是问卷内容。正式生产地址为：

`https://sequence-prediction-study.netlify.app/`

### 12.2 静态资源

全部 Graph、Video 和终帧随站点部署到 Netlify：

- 不从 `raw.githubusercontent.com` 加载；
- 不更改素材二进制内容；
- PNG/GIF/终帧使用长缓存；
- HTML 不使用长期缓存，保证正式更新可及时生效；
- 素材哈希回归检查用于防止构建过程改写研究材料。

### 12.3 服务端组件

- Netlify Functions：格式分配、应急登记、答卷提交、后台登录、统计和导出；
- Netlify Database：随机化账本、权威答卷、冲突、Forms mirror outbox、后台会话/审计；
- Netlify Forms：正式与测试答卷的第二份冗余镜像；
- Scheduled Function：重试尚未完成的 Forms 镜像；
- GitHub：代码版本与发布审查，不承担正式答卷数据库职责。

### 12.4 正式开关

正式发放至少包含两个独立开关：

- `MMQ_FORMAL_COLLECTION_OPEN`：是否允许新参与者领取正式分配；
- `MMQ_SUBMISSIONS_OPEN`：是否允许正式答卷写入权威数据库。

准备和测试阶段均保持关闭。打开或关闭环境变量后必须重新生产部署，因为已部署 Function 不会自动获取新值。

## 14. 发放期间的运行规则

建议先进行小批次正式发放，而不是一次性放出全部样本：

1. 第一批 10–20 人；
2. 核对权威数据库答卷、随机化账本和 Forms 镜像；
3. 检查每人 5 条唯一试次、格式一致和 Catalog hash；
4. 检查冲突、应急随机和素材加载失败；
5. 通过后再发下一批。

暂停下一批的条件包括：

- 重复出现空白页、Video 无法加载或提交无法确认；
- 任一正式会话不是 5 条唯一试次；
- 同一会话的 5 题格式不一致；
- Catalog 或素材 hash 不匹配；
- 应急随机超过 1% 或连续出现 3 次；
- 同一运营商或地区连续出现两例技术失败；
- Netlify 用量接近团队设定阈值。

每批次至少保存：

- 数据库权威导出；
- Forms 原始导出；
- 随机化摘要；
- 冲突和镜像状态；
- 两份加密本地备份。

## 15. 已知限制与不得过度解释的事项

1. **3000 个分配位不是 3000 份完成问卷。** 退出、清缓存、无痕、换设备会消耗额外位置。
2. **可变区组平衡的是分配数，不是完成数。** 正式报告应同时给出 assigned 和 submitted。
3. **浏览器令牌不是自然人唯一身份。** 它不能完全阻止同一人换设备或清数据后再次进入。
4. **本地应急随机不在预生成区组顺序内。** 必须单独报告并进行排除应急样本的敏感性分析。
5. **普通 Netlify 在中国大陆不保证全国稳定可达。** 一次本地或团队测试通过不能证明所有地区和运营商均稳定。
6. **Netlify Database 与 Forms 是境外托管服务。** 技术可用性不等同于已满足机构、伦理或数据合规要求。
7. **网页完成不等于研究获准发放。** 当前材料中未核实伦理审批号、批准日期或机构正式授权；研究负责人须在发放前自行确认。
8. **平台来源 IP 不应被自动解释为参与者身份或研究变量。** 是否使用该信息应事先明确，而不是在分析阶段临时决定。
9. **技术日志主要用于质量控制。** 对加载时长、重试或全屏行为的实质解释应在统计分析计划中预先界定。
10. **冲突表证明发生过不同 hash 的重复提交，但不保存第二份完整尝试内容。** 这样可避免把被拒绝或疑似篡改的 payload 再持久化一份；代价是研究者只能依据原答卷、尝试 hash、来源 IP 和部署元数据审计冲突，不能在后台逐字段比较被拒绝内容。

## 16. 版本冻结与变更规则

正式收数开始后，不得在同一版本下静默修改：

- 刺激值；
- Catalog；
- 素材文件；
- Pool 或题目抽取规则；
- 呈现格式；
- 随机表；
- 验证条件；
- 参与者文案的实质含义；
- 数据字段的定义。

如果必须修复：

1. 先关闭新分配；
2. 保存当前生产 deploy 与数据库快照；
3. 记录问题、影响范围和发现时间；
4. 增加明确版本号；
5. 完成回归测试；
6. 决定修复前后数据能否合并分析；
7. 再重新开放。

不可在原版本名下重新生成私有随机表，也不可覆盖历史权威答卷。
